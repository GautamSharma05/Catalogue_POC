# AI Usage Notes

## Tools and models

### What is AOS (Agentic Operating System)?
**AOS** stands for **Agentic Operating System** — a structured orchestration harness and workflow framework designed to guide, constrain, and supervise autonomous AI coding agents. For reviewers unfamiliar with the term, AOS acts as an agentic operating layer that standardizes software engineering workflows through custom, specialized "skills" (commands), ensuring that architectural planning is strictly decoupled from code execution, human-in-the-loop approval gates are enforced, and test-driven verification is mandatory.

The key components used during this project include:
- **Custom Skills (`/aos-plan` & `/aos-execute`):** Purpose-built skills governing the end-to-end engineering lifecycle:
  - **/aos-plan (Planning & Specification):** A dedicated planning skill that ingests and normalizes unstructured briefs, maps requirements to discrete traceability ledgers (`REQ-001` through `REQ-018`), defines system architecture, models data flows, and partitions work into dependency-ordered workstreams. Crucially, `/aos-plan` enforces an explicit approval gate: the agent is barred from generating implementation code until the human engineer inspects and approves the technical plan.
  - **/aos-execute (Deterministic Execution):** A disciplined execution skill that takes the approved plan and implements it incrementally across isolated workstreams. It enforces verifiable progress checkpoints at each step—triggering compilation, linting, unit tests, and Playwright verification before advancing.
- **pi coding agent:** The terminal-based coding agent operating within the AOS environment, executing the `/aos-plan` and `/aos-execute` workflows.
- **AOS Router:** The model-routing and gateway layer within the Agentic Operating System responsible for dispatching tasks and prompt contexts to the appropriate underlying LLMs.

## Key prompts and moments that shaped the work

The following examples demonstrate how I directed the agent, where I exercised architectural judgment, and how I validated the system output:

1. **Ground-Truth Requirement Ingestion (Zero-Assumption Extraction)**  
   Instead of allowing the AI to hallucinate or extrapolate requirements from an incomplete prompt or directory name, I mandated strict programmatic ingestion of the primary source-of-truth: the provided assessment PDF brief. When standard shell extraction utilities (`pdftotext`, `PyPDF2`) were unavailable in the runtime environment, I directed the agent to execute a low-level parsing script using `zlib` and `pypdf`. This guaranteed that all downstream architectural planning, domain modeling, and test assertions were mapped directly to verbatim stakeholder requirements (`REQ-001` through `REQ-018`) rather than unverified assumptions.

2. **Decisive Architectural Trade-Off Analysis & Stack Selection**  
   The brief offered flexibility across multiple frontend and backend stacks. Rather than introducing review latency or letting the model make arbitrary technical choices, I conducted an immediate architectural trade-off evaluation:
   - Selected **React + TypeScript** paired with **Node.js/NestJS + TypeScript** to establish single-language end-to-end type safety and maximize development velocity.
   - Explicitly bypassed mobile/desktop native simulator targets (iOS/Android) in favor of a containerized web architecture, ensuring reviewers could spin up and evaluate the entire distributed stack within minutes with zero local machine friction.
   - Formalized this decision immediately in architecture records (`DECISIONS.md`) to maintain clear rationale traceability.

3. **Enforcing Human-in-the-Loop Governance via Gated Planning (`/aos-plan`)**  
   To prevent "agent runaway" (unconstrained, speculative code generation), I enforced strict phase separation using the custom `/aos-plan` skill. I instructed the agent to break the system into three isolated, dependency-ordered workstreams: Backend & Catalogue Domain, Enquiry & Notifications, and Web Client & Local Delivery. Each stream was required to document its proposed file operations, interface contracts, and acceptance criteria upfront. Crucially, I maintained a strict approval gate: the agent was barred from generating implementation code until I reviewed, validated, and signed off on the technical plan.

4. **Architectural Boundary Design under Zero-Paid-Account Constraints (`EmailPort`)**  
   The assessment brief required that customer enquiries notify a sales inbox, but explicitly forbade requiring the reviewer to have paid third-party accounts or external API keys (e.g., SendGrid, AWS SES). Rather than hardcoding console logs or stubbing out an SDK directly inside the controller, I directed the agent to design a clean hexagonal seam:
   - Defined `EmailPort` as an abstract boundary in the domain layer.
   - Built `ConsoleEmailAdapter`, which logs delivery metadata to stdout and concurrently appends atomic JSON lines to a mounted volume path (`tmp/sent-emails.log`).
   - This satisfied the end-to-end asynchronous enquiry lifecycle, allowed reviewers to inspect outgoing enquiries with a single `docker compose exec api cat tmp/sent-emails.log` command, and ensured a cloud provider (such as Amazon SES) can be introduced via configuration without altering a single line of domain or controller logic.

5. **Deliberate Architectural Evolution: From Prototype Spike to Hexagonal Domain**  
   The initial backend was bootstrapped in Express to validate baseline data contracts against the external Fake Store API quickly. However, recognizing that enterprise maintainability requires robust dependency injection and modularity, I challenged this choice and mandated an intentional migration to **NestJS**. I guided the structural refactoring to implement a true **Hexagonal Architecture (Ports & Adapters)**:
   - Replaced TypeScript interfaces with abstract classes for `ProductCatalogPort` and `EmailPort` so NestJS's DI container could resolve them as first-class runtime injection tokens.
   - Bound concrete adapters (`FakeStoreCatalogAdapter`, `ConsoleEmailAdapter`) via module providers, enabling clean dependency inversion and frictionless test-fixture swapping without relying on brittle runtime monkey-patching.

6. **Systemic Scope Management & Component-Driven UI Migration (`shadcn/ui`)**  
   When evaluating the user interface layer, I identified that custom, hand-rolled CSS classes (`theme.css`) introduced technical debt, inconsistent focus rings, and poor accessibility primitives. I initiated a scope expansion to migrate the frontend to **Tailwind CSS v4** and **shadcn/ui** (Radix UI primitives). When the agent prompted whether to apply this incrementally or systematically, I opted for an atomic, full-codebase migration. This established accessible dialog modals (focus trapping, keyboard escape listeners), standardized typography and design tokens, and clean form controls across every page without leaving fragmented legacy styling paradigms behind.

7. **Multimodal Visual QA & Cross-Viewport Defect Triage**  
   I refused to rely solely on headless test suites or compile checks as proof of UI correctness. I established an automated visual QA loop using Playwright to capture rendered screenshots across responsive breakpoints (desktop 1280px vs. mobile 375px). This visual scrutiny uncovered real-world rendering defects invisible to DOM assertions:
   - Identified text legibility failures caused by dynamic background imagery on category cards.
   - Detected horizontal layout overflow on mobile navigation without clear scrolling affordances.
   - Uncovered severe product image distortion where `object-cover` forced portrait-oriented merchandise into square containers, which I instructed the agent to remediate systematically across all product cards and category grids.

8. **Combating Automation Bias via Rigorous Requirements Traceability**  
   While automated unit and integration suites were passing green, I performed a manual cross-audit of the implemented UI against the original acceptance criteria in the specification. I discovered a subtle functional omission: the search combobox supported debounced autocomplete, full keyboard navigation, and Enter-to-submit, but lacked an explicit clickable "Search" button specified in the prompt ("WHEN I click the search button"). Because tests authored against an implementation only test what exists, this audit highlighted the danger of **automation bias**. I directed the agent to implement the explicit button and authored dedicated E2E specs to ensure complete requirement coverage.

## How I validated AI-generated work

My validation was primarily test-driven, supported by browser-based checks and review of concrete changes:

- Used the planned unit, integration and end-to-end tests to exercise the application and its important boundaries.
- Used Playwright browser runs and screenshots at desktop and mobile widths to inspect rendered behaviour, not just whether the code compiled.
- Compared the implemented experience back against the original acceptance criteria. This comparison caught the missing clickable Search button.
- Investigated unexpected working-tree changes with Git history and diffs rather than automatically including unexplained changes in a commit.
- Checked the final committed Git message after a shell-quoting mistake described below.

This was not a claim that every generated line was manually inspected. The main validation approach was automated tests plus targeted browser and Git-based checks, with issues escalated and corrected when those checks or my own use of the application exposed them.

## Where the AI got things wrong, and how the issues were caught

- **A generated use-case test contained stale code.** The first draft of `catalogue.use-cases.test.ts` included a leftover fragment (`useCases.isNeverCalledDirectly ?? ...`) from an earlier design idea. It was caught while reviewing the generated test before running it and removed with a targeted edit. The lesson was that generated tests also need scrutiny; their presence is not evidence that they are valid.

- **The initial TypeScript module setup added avoidable complexity.** The Fake Store adapter API package was first configured as an ESM Node project with `moduleResolution: "bundler"` and `.js`-suffixed relative imports. For this small Express application, that added unnecessary module interop complexity. It was simplified to a CommonJS TypeScript setup before implementation progressed further.

- **The first visual review did not catch all image and layout defects.** `object-cover` looked plausible from the code but cropped a portrait ring photograph into an unrecognisable portion when rendered in a square thumbnail. I caught this in the running UI and shared screenshots; the agent traced the issue and also checked the category tiles for the same root cause. A separate screenshot exposed the footer sitting too high on short pages because the page shell did not use a flex-column layout.

- **Unexpected Git changes required investigation.** An unexplained `m-2` class change in `EnquiryForm.tsx` and a later deletion of `NESTJS_MIGRATION.md` appeared in the working tree. The agent checked `git log` and `git show` before acting. One change was reverted because its origin was unexplained; the deletion was confirmed as an intentional change I had made outside the agent session and was then handled accordingly. The principle was not to commit unexplained diffs merely because `git add -A` would include them.

- **Shell quoting corrupted a commit message.** Backticks in a multi-line `git commit -m` message triggered shell command substitution. Some snippets were treated as commands, and command output was inserted into the message. This was caught by reading the committed message with `git log --pretty=full`; the commit was amended using a file with `git commit --amend -F` to avoid shell interpretation.

- **The agent and existing tests missed a literal acceptance criterion.** Search was usable through Enter and suggestion selection, but the required clickable Search button was absent. A deliberate acceptance-criteria-to-UI review caught it. The tests had not failed because they only covered the interactions that had been implemented. This reinforced the need to derive tests from requirements, not only from the implementation plan.

## Time spent

The total time spent was approximately **4 hours 20 minutes**. The work exceeded the suggested 2–3 hour time-box because I deliberately expanded the scope after the baseline PoC to improve the backend structure, UI system and validation.

| Phase | Time | Activities |
|---|---:|---|
| Planning | ~40 min | Extracting and normalising requirements, choosing the stack, modelling the domain and planning the work streams |
| Building | ~2 hr 30 min | Core NestJS API and React web application, followed by the deliberate architecture and UI improvements |
| Testing | ~35 min | Unit, integration and Playwright end-to-end testing |
| Reviewing and polish | ~35 min | Browser screenshot checks, layout fixes, Docker/build refinements and documentation |
| **Total** | **~4 hr 20 min** | |

The baseline requirements were prioritised first. The additional time went into improvements intended to make the result a more useful foundation rather than a disposable demonstration.
